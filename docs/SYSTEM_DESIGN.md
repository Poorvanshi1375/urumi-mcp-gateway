# System design and tradeoffs

How the gateway is built and why, and what changes for production. Security is covered in [THREAT_MODEL.md](THREAT_MODEL.md).

## 1. Architecture choices

**One platform service, not three.** The MCP gateway (`/mcp`), the dashboard API (`/api`), the chat agent and the React build are one Node 24 process (Fastify 5, MCP TypeScript SDK v2). They share one in-process gateway core, so an MCP client and the chat agent cannot take different paths. One origin also means no CORS, one Ingress host and a strict Content-Security-Policy. It runs as 2 or more replicas.

**The gateway core.** `services/platform/src/gateway/mcp.ts` exposes two functions that every entry point uses:
- `listToolsFor(principal)`: tools of enabled, connected servers, minus tools the caller's role may not use, minus tools waiting for re-approval (tool pinning);
- `callAsUser(principal, source, name, args)`: write the audit row first (the call is refused if that fails), resolve the name, check permission, route with a timeout and a per-server concurrency cap, complete the audit row, update metrics.

`/mcp` builds a fresh stateless MCP server per request on top of these; the chat agent calls them directly with the signed-in user as principal. Permissions, timeouts and audit therefore live in exactly one place.

**Two ways to authenticate, one principal.** `/mcp` accepts a user's API key or an OAuth access token (feature flag). Both resolve to the same principal (user, role), so permissions, rate limits and audit do not depend on how the client signed in. The gateway is its own OAuth authorization server for its existing users: discovery from the 401, dynamic client registration, PKCE, consent in the dashboard, opaque tokens stored hashed and checked on every request (no JWTs, so revocation is immediate and there is no signing key to manage).

**Postgres for all shared state.** Users, sessions (hashed), API keys and OAuth codes and tokens (SHA-256 only), registered servers (credential encrypted with AES-256-GCM), tool permissions, tool pins, the audit log, the activity log and sign-in throttling. Replicas keep only caches and re-read on `NOTIFY` (registry, permissions, pins, re-check requests). Schema changes are Drizzle migrations applied by an init container under an advisory lock, as the database owner; the gateway itself connects as a restricted role (`urumi_app`) that can add and complete audit rows but not delete or rewrite them. The provisioner connects as `urumi_provisioner`: its own tables and, through row-level security on `upstreams`, only the servers it manages.

**Our own MCP servers speak only to what they need.** woo-mcp calls the WooCommerce REST API v3 with OAuth 1.0a signatures over plain HTTP inside the cluster (WooCommerce only accepts key and secret as Basic auth over HTTPS, so in-cluster calls must be signed; the signature covers the store's configured home URL, so that URL is a value per environment). REST gives a stable, versioned contract with WooCommerce's own validation, and woo-mcp needs no access to WordPress's files or database. woo-mcp also computes order counts and exact totals itself (BigInt over minor units, never across currencies) and says whether a list is complete, so the model reports figures instead of adding up money. ship-mcp is a small deterministic shipping service whose `get_order` deliberately collides with woo-mcp's.

**Two Helm charts, one namespace.** `urumi-store` (WordPress, MySQL, setup Job) and `urumi-platform` (gateway, Postgres, our MCP servers). Separate releases mean a gateway rollback can never touch the store's data. Isolation inside the namespace comes from NetworkPolicies on pod labels, not namespace boundaries.

**Secrets outside Helm.** `scripts/secrets.sh` creates every Secret; the charts reference them by name. No secret value is in git, in values files or in Helm's release history.

**Hosted servers through a separate provisioner.** Admins can add an MCP server by container image. The gateway, which faces the internet, never touches Kubernetes: the dashboard's API writes a desired-state row (`hosted_servers`) and wakes the provisioner, a separate pod and the only one with a Kubernetes token. It claims each row under a lease, runs idempotent steps (namespace `mcp-<prefix>`, role binding, quota, NetworkPolicies, Secret, Deployment, Service), registers the server as a managed upstream, and marks it Ready only once the gateway has connected and listed its tools (a stdio server runs behind a small bridge that serves it over HTTP); every write is a compare-and-set on the row's state, so a Delete stops a running install. Its rights end at this install's tenant namespaces, enforced by RBAC and by five admission policies at the API server, and it connects as its own database role that sees only the servers it manages. Full design, the fence and its checks: [provisioner.md](provisioner.md).

**Bonus stores through the same provisioner.** An admin creates a store from the dashboard; the provisioner installs the same `urumi-store` chart as the default store with Helm, in its own namespace `store-<name>` with restricted Pod Security and a quota, including the store's own woo-mcp, and registers that server as `<name>`. Each store has its own database, volumes and secrets, and its MCP server reaches only its own WordPress. Results carry the store's title and URL, and the chat agent is told never to mix figures from different stores; with many tools, chat searches for the ones it needs.

**Chat asks before writes, and has a second model provider.** The agent runs reads at once; a call that may change data (any tool that is not read-only by a trusted server's hint) becomes a proposal stored server-side and shown as a card, and runs only when the user who asked confirms it, through the same audited path (`platform.chat.confirmWrites`). Gemini's models are tried in order, then an OpenAI-compatible fallback (Groq), only before any tool has run in that answer, so a write never runs twice (`platform.chat.fallback`).

## 2. Tool aggregation and routing

1. **Registry.** Servers live in Postgres: prefix (2 to 12 lowercase letters or digits, unique), URL, auth type (none, bearer, custom header) and encrypted credential. Our two servers and DeepWiki are registered on first start; admins add more in the dashboard.
2. **Connections.** The gateway is an MCP client with one pooled connection per server (Streamable HTTP). It adds the server's own credential, decrypted only at that moment. The client's API key, OAuth token or session cookie is never sent upstream (checked by `credential-isolation-check`), nor are the client's other headers or query string.
3. **Health loop.** Every 5 s (local) or 10 s (VPS) each server is listed independently, with at most one check in flight per server, so a slow server delays nobody. The result is cached in memory and in Postgres, so `tools/list` never waits on an upstream.
4. **Naming.** Each tool is exposed as `<prefix>__<name>`. Names keep only `[A-Za-z0-9_-]` and at most 64 characters (what strict LLM providers accept); a name that has to be cut, or collides after cleaning, gets an 8-character hash suffix. A per-server map from exposed name to the upstream's own name is used to route back. Descriptions and the descriptions inside input schemas are cleaned of invisible characters (control, bidi, zero-width, TAG and variation-selector characters) and capped at 1024 characters, and each description is prefixed with `[Server name]`. Only known tool fields are forwarded; an upstream's `_meta`, icons and extensions are dropped.
5. **Collisions.** Because of the prefix, `woo__get_order` and `ship__get_order` coexist; the prefix is the documented scheme, and routing splits on the first `__` (tool names may contain `__` themselves).
6. **Routing a call.** `callAsUser` writes the audit row (`pending`; no row, no call), splits the name, finds the server's state, maps the exposed name back, checks the caller's permission (members: the explicit rule, else the member default, which in the shipped values allows only tools the server marks `readOnlyHint`, and only from a server whose annotations are trusted: the release's own woo and ship, or one an admin vouched for), and calls the upstream with a 20 s timeout. Results over 100,000 characters are cut, with a note; the upstream's `_meta` is not forwarded. With `platform.features.validateArguments` (on in both values files), the arguments are first checked against the tool's own input schema: a malformed call fails at once with a precise message ("arguments/id must be integer"), is audited as `rejected` and never reaches the server; a tool whose schema is not valid JSON Schema is hidden, with the reason on the Servers page, without hiding the server's other tools. Each `/mcp` request (and each chat message) has one request id: returned to the client as `x-request-id`, stored on its audit rows, and sent upstream as W3C trace context (`_meta.traceparent`), which woo-mcp and ship-mcp log, so one call can be followed through all three. One audit row is written whatever happens.
7. **Change propagation.** Disabling a server, changing a permission or approving a tool writes to Postgres and sends `NOTIFY`. Each replica reloads and sends `tools/list_changed` to its connected clients; Claude Code re-lists within about a second. The chat agent reads the tool list per message.

**Tool search mode** (feature flag, on in both values files): for many servers, `/mcp?mode=search` exposes only `gateway__search_tools` (keyword ranking of the caller's own tools) and `gateway__call_tool` (the same `callAsUser` path).

## 3. Failure handling

| Situation | What happens |
|---|---|
| A server is slow | Its call times out after 20 s with "Server X did not answer within 20 s". For a tool not marked read-only the message adds that the request was sent and may have completed, so an agent checks before repeating a write; the gateway never retries. Health checks time out after 8 s. Other servers' calls and `tools/list` are unaffected (independent checks, cached lists). Tested with a 25 s artificial delay: woo answered in about 100 ms meanwhile. |
| A server dies | The next health check fails. Refused connections, unknown hosts, auth failures and connect timeouts to in-cluster addresses mark it Unreachable at once; other errors need two failures in a row, so a single network blip (common with remote servers) does not hide its tools. Its tools leave `tools/list`; calls fail in milliseconds with the reason. The replica that notices tells the others through `NOTIFY` so they re-check at once. |
| A server comes back | The next health check reconnects and its tools return; clients get `tools/list_changed`. The dashboard keeps the last outage ("recovered 4 s ago after 16 s unreachable"). |
| A pod is killed | Its Deployment replaces it, usually before the next health check. Stopping the server entirely (0 replicas) shows Unreachable within one health interval (measured 8 to 16 s on the VPS). |
| A call fails mid-way | `isError: true` result with a one-line reason, audited as `tool_error`, `timeout` or `upstream_unreachable`. A failed call also triggers an immediate health check. |
| A server sends a huge answer | Reading stops at 10 MiB (`platform.upstreamMaxResponseBytes`), before parsing; the call fails at once with "returned more than 10 MiB; the call was stopped" and the connection is reopened. Measured in the unit check: 34 ms with a 1 MiB cap. |
| One server gets too many calls | At most 8 calls in flight per server and 32 waiting (up to 2 s); beyond that a call is refused at once as `busy`, so a stuck server cannot pile up hundreds of open requests. Other servers are unaffected. |
| The chat model is out of quota or slow | Each model in `platform.chat.models` is tried in turn (20 s each), then the OpenAI-compatible fallback (`platform.chat.fallback`, Groq; 30 s) if its key is set. Moving to the fallback happens only before any tool has run in that answer: replaying calls into another provider could run a write twice, so after a tool call a failure ends the answer with "the language model stopped answering after the tool calls above". The fallback keeps the rest of the answer (Gemini's thought signatures never meet another provider) and Gemini rests for 60 s, per replica. If Groq refuses the model's own tool call for breaking a schema (`tool_use_failed`), the reason goes back to the model for one more try. If all fail, the message names the first cause, e.g. "The language model's quota is used up (gemini-3.5-flash: quota used up; gemini-3.5-flash-lite: no answer within 20 s)", instead of a bare timeout: a used-up daily quota sends every request to the slower fallback. |
| The chat model wants to change data | With `platform.chat.confirmWrites` (on in both values files) the write becomes a proposal row (`chat_proposals`: user, tool, exact arguments, expiry) and a card in the chat; reads in the same round still run, a second write is refused, and the turn ends. `POST /api/chat/proposals/:id` with `confirm` claims the row atomically and runs the stored call through `callAsUser` (permissions, pinning, rate limit and audit apply again), then one model call without tools reports the result under the asking message; `reject` answers at once without the model. A new message declines a waiting proposal. |
| The chat model repeats a call within one answer | The identical call (same tool, same arguments in any order) runs once; the repeat reuses the result, so a repeated write is not duplicated. Failed calls are not reused. |
| An unknown tool name (a model invented it) | Refused with up to three suggestions from the caller's own tools ("Did you mean ..."). |
| Postgres is down | Readiness fails and Traefik stops routing to the gateway; calls already routed finish. The gateway reconnects its `LISTEN` connection when Postgres returns. |
| A gateway replica is replaced | Rolling updates wait for readiness; a `preStop` pause lets Traefik stop routing first; a PodDisruptionBudget keeps one replica. Measured: no failed requests during a broken-image upgrade and rollback. |
| An upstream changes a tool definition | With tool pinning on, the changed tool is hidden and refused until an admin approves the new version. The servers deployed with the platform (woo, ship) are not pinned, so upgrading them never hides their tools. |

On k3s we measured something local k3d hides: after a Service's last pod disappears, new connections to it are dropped (not refused) for 20 s or more. The connect-timeout rule for in-cluster servers and short-lived upstream sockets exist because of that.

## 4. Scaling

`/mcp` keeps no session state, so any replica can serve any request; this was tested with MCP Inspector and Claude Code, each of which was served by both replicas. Replicas run their own health checks and synchronise registry, permission, pin and health changes through Postgres `NOTIFY`, converging in about a second. Rate limits (120 requests per minute per key, burst 60; 10 chat messages per minute per user) are token buckets in Postgres, updated in one statement per request with Postgres's clock, so they are exact across replicas (measured: 180 requests spread over 2 replicas, 61 allowed: the burst of 60 plus one second of refill). If Postgres cannot answer, each replica falls back to its own in-memory bucket. Sign-in throttling is in Postgres too. Failed `/mcp` authentications are throttled per client address in memory (30 a minute per replica, then 429 before any key lookup): a load shield, not an exact limit.

## 5. What changes for production

| Area | Local | Production-like VPS | Real production |
|---|---|---|---|
| DNS and hosts | `*.localhost` | `*.<ip>.nip.io` | a real domain; set `store.host`, `store.homeUrl`, `platform.ingress.host` |
| Ingress and TLS | Traefik on the node's ports 80/443 (`hostPort`), plain HTTP | same Traefik setup, Let's Encrypt via cert-manager, http redirected to https; each client's real address reaches the gateway | same, or the cloud's load balancer (with the proxy protocol or `X-Forwarded-For` from a trusted hop) and certificates |
| Storage class | `local-path` (node disk) | `local-path` (instance disk; terminating the instance loses data) | a replicated or cloud block storage class, backups of MySQL and Postgres |
| Secrets | `scripts/secrets.sh`; encrypted at rest in k3s (`--secrets-encryption`) | `scripts/secrets.sh` on the node; encrypted at rest in k3s | External Secrets from a vault, or sealed-secrets; the charts only need Secrets with the right keys |
| Images | built and loaded into k3d | copied over SSH | a registry (for example GHCR) with pinned tags |
| Gateway replicas | 2 | HPA 2 to 4 | same, plus pod anti-affinity across nodes |
| Databases | single Postgres and MySQL pods | same | managed databases or replicated charts |
| Rate limits | shared (Postgres) | shared (Postgres) | same; Redis if Postgres load from limiting ever matters |
| Metrics | `/metrics` on a private port | same | scraped by Prometheus (`networkPolicy.metricsScrapers`), dashboards in Grafana |

This is checked from the charts, not only described: `node scripts/values-diff.mjs` renders both charts with `values-local.yaml` and `values-prod.yaml` and lists every field that differs. Today that is 29 fields: hosts and URLs (including the gateway's public URL, the OAuth issuer, and the bonus stores' home and signing URLs), the number of bonus stores (3 on k3d, 2 on the 8 GiB VPS), the store Service's extra local port (9080, the local home URL's port), TLS (certificate annotations, `tls` blocks, the http to https redirect Middleware), replicas versus autoscaling, and the health-check interval. Storage classes, resources, probes, security contexts and NetworkPolicies are identical. The script fails on any other kind of difference, and runs in CI with `scripts/chart-invariants.mjs` (probes, limits, non-root, no API tokens, no Helm-rendered Secrets, ClusterIP-only internals).

## 6. Known limits

- The first version of a server's tools is trusted (tool pinning starts from it), and tool results are only capped and delimited, not reviewed.
- Members can see every server's name and tool list (not URLs or credentials).
- 2025-revision MCP clients (Inspector, Cursor) see tool-list changes on their next list, not by push; calls are still refused at once.
- Third-party images (Postgres, MySQL, WordPress) are pinned by tag and only reported by the CI scan: on 21 October Trivy found fixable critical and high findings in them (postgres 1/25, mysql 2/49, wordpress 3/100). Our three images carry none (the package managers, whose bundled packages were the only findings, are removed). Moving to newer tags is the fix; we do not patch upstream images.
- OAuth: the app name on the consent page is self-declared (no client ID metadata documents), tokens carry the user's full rights (no narrower scopes), and over plain HTTP clients accept it only on localhost.
- Bonus stores are served over plain HTTP (a certificate per store on nip.io would hit Let's Encrypt's rate limit), and the VPS has room for two besides the default store.
